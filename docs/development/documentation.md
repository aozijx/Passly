# 文档维护约定

## 分类与命名

- 目录使用稳定主题：`architecture`、`data`、`security`、`features`、`development`、`decisions`、`reviews`。
- 文件名使用小写 kebab-case；目录内 `README.md` 只作为索引。
- 一个主题只有一份“当前实现”文档，避免 Design、Implementation、outline 并存。
- 类与包名以仓库当前代码为准；版本号、字段表等易漂移信息尽量链接源码而不是整段复制。
- 多流程主题可以建立目录和 README 索引；只有职责可独立变化时才拆文件，行数不是拆分理由。
- `specs`、`plans` 只用于工作中的临时材料。正式合同或实现落地后，内容归入稳定主题页并删除临时文件。

## 内容结构

主题文档优先采用“状态、职责、边界、流程、失败/清理、相关实现”。复杂流程使用 Mermaid，代码只保留能解释
契约的关键片段。迁移旧文档前先核对生产代码、Manifest、Gradle、Proto/Room schema、资源和行为测试；移动文本
不等于验证正确。

状态统一使用：

- `状态：当前实现`；
- `状态：已批准，尚未实现`；
- `状态：过渡中`，并明确分隔当前与目标。

外部 Android API、权限、存储、生命周期和平台回调语义需要同时核对官方 Android 文档。现有 prose 不能覆盖
生产源码；只检查源码字符串的测试也不能单独证明运行时行为。

ADR 统一包含：状态、日期、背景、决策、后果、备选方案和关联资料。已发布 ADR 不删除；决策变化时新增 ADR，并用
`Superseded by` 建立关系。

## 校验

修改文档后至少检查：

- 相对链接目标存在；
- 类名、包名和 Gradle 任务仍存在；
- Mermaid 节点文本不依赖大段实现代码；
- “已实现”和“计划中”有清晰区分；
- 没有密钥、签名凭据或本地路径进入文档。
- 没有重复定义另一个主题拥有的协议；跨主题使用链接。
- dated 计划、完成清单、旧类名和一次性命令没有残留在正式文档。
