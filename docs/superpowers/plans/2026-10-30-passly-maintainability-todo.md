## Task 26：明确 Runtime Session 生命周期转换的并发所有者

- [ ] 让数据库资源状态机的并发合同单一且可执行：要么 `RuntimeSessionManager/SessionLeaseGate` 自己串行化 open、resume、soft-lock、seal 和 close 转换；要么将外部互斥前置条件明确限制在唯一可见的适配入口，并证明所有调用者始终共用同一互斥。不能只保护 `handle` 指针的短临界区，却让资源创建和终止转换并行竞争。
- [ ] 使用屏障式并发测试覆盖两个首次 `unlock()` 同时通过 `resumeIfOpen()` 且分别执行 `resource.open()`、新 open 与 seal 并发、已打开 handle 的 `resumeIfOpen()` 与 seal 在“检查 handle/发布 UNLOCKED”间交错、soft lock/resume 竞态；终态必须与最后一个获准转换一致，最多保留一个资源句柄，不丢弃未关闭句柄，也不能在 seal 已返回后重新发布 UNLOCKED。
- [ ] 明确 `RuntimeSessionManager.seal()` 在 drain 等待期间收到取消的合同：现在 seal 先发布 SEALED，再在可取消的 `withTimeoutOrNull` 中等待 leases；取消会直接跳过 `close()`，留下 SEALED 状态与仍持有的 handle。要么 Runtime 自己保证终止清理，要么将该前置条件限制在可审查的会话入口并证明调用者都在 NonCancellable 区调用；不能让公开 Runtime API 隐式依赖上层清理纪律。
- [ ] 闭合 lease timeout 后仍有非合作操作存活的资源安全边界。当前 `seal()` 取消所有 lease owner 后只再等待固定 100ms；等待超时结果被忽略，随后无条件 `close()`。若 read/write block 在 `NonCancellable` 或不可中断 native/IO 调用中继续使用 handle，`activeLeases` 仍未归零；`resolveHandle()` 只在取句柄时短暂持有 `resourceMutex`，所以 `close()` 持锁并不会等待已进入的 `SessionResource.transaction/read` 实际使用结束。确定不能关闭仍在被操作使用的 handle；需定义剩余 lease 的 owner、SEALED/close 结果和后续回收/重试行为，若要强制终止则由资源端提供可验证的 abort 合同，不得把固定 grace 超时当作 lease 已结束。
- [ ] 用不响应取消的屏障式 `SessionResource` 回归覆盖首次 drain timeout 与 post-cancel grace 到期：在活动 read/write block 内进入 `NonCancellable` 并停在闸门上，调用 seal 后断言底层资源没有被并发 close、SEALED 后新 lease 被拒绝；释放操作后验证 handle 恰好关闭一次、lease 归零、事件/返回结果如实体现延迟或终止失败。保留现有及时响应取消的 observer/write 测试，不把它们当作非合作操作合同。
- [ ] 定义 soft-lock 对已取得 lease 的读、写与长期观察的完成语义。当前 `softLock()` 只把状态设为 SOFT_LOCKED，不等待、取消或排空 active leases；新 lease 会被拒绝，但已进入 `read()`/`write()` block 的操作没有锁后检查，可能在认证状态已变为 Locked 后才返回或提交。明确 lock API 是否必须等待既有操作收尾，以及结果可否在锁后到达调用方；据此选择排空、可控取消或调用端 owner/token 作废，不得仅依赖“已禁止新租约”声称锁定已闭合。
- [ ] 保留 `VaultSessionController` 对认证、reset、锁定的会话级串行化；如果 runtime 内增加状态转换互斥，核对取消等待、open 中取消后的 close、lease 排空和数据库重置 seal→文件操作→unlock 的锁顺序，避免将内部资源锁和外部会话锁交错成死锁。运行 Runtime Session、Security Session 与 Data Reset 定向测试及架构门禁。

**证据：** `SessionLeaseGate.open()` 在 `resource.open(key)` 期间不持有 `resourceMutex`；它仅在资源创建后用该锁发布 `handle`，再独立把 `lockState` 设为 UNLOCKED。两个首次 `unlock()` 可在各自的 `resumeIfOpen()` 都观察到 `handle == null` 后并行创建资源，随后后一个发布会覆盖前一个句柄。并发 seal 可先设置 SEALED、看到空句柄并返回，之后 open 仍可能发布新句柄并解锁。当前 production call sites 由 `VaultSessionController.mutex` 串行，数据库 reset 的直接 seal/unlock 又在 `withExclusiveDatabaseReset` 持有同一 mutex 时执行；因此这是 Runtime 通用状态机缺少自有并发合同/独立回归的风险，并非已证明的现行 UI 竞态。`DatabaseSessionLifecycle` 和 `RuntimeSessionManager` 公共声明均未记录调用者必须串行这一前提。

**新增状态交错证据：** `resumeIfOpen()` 先在 `resourceMutex` 内判断 `handle != null`，释放后才获取 `leaseMutex` 发布 UNLOCKED。若它读到已有 handle 后暂停，`seal()` 可先发布 SEALED、排空后关闭并清空该 handle、完整返回；迟到的 resume 随后仍会发布 UNLOCKED，此时状态为 UNLOCKED 而资源为空，且 transition event 顺序与最终状态相反。现有 Runtime 测试只顺序覆盖 soft-lock 后 resume 与 seal，没有暂停在 handle 检查/状态发布之间的屏障用例。另 `seal()` 发布 SEALED 后在可取消的 `withTimeoutOrNull(timeout)` drain loop 中等待；调用方此时取消会从循环向外传播并跳过其后的 `close()`，令 handle 留存但锁状态 SEALED。当前 App 生产路径由 `VaultSessionController.lock()/rollbackStagedSession()` 或 `VaultDatabaseResetController.reset()` 在 `NonCancellable` 区执行 seal，所以此取消窗尚非已证实的现行调用故障；`RuntimeSessionManager.seal()` 本身是公开 suspend API，未记录这一调用前置条件，故需在 API owner 与测试中闭合。

**新增 post-cancel lease 证据：** `SessionLeaseGate.seal()` 在初次 drain timeout 时调用 `leaseOwners.keys.forEach(Job::cancel)`，然后以 `withTimeoutOrNull(POST_CANCEL_GRACE_MS)` 等待 `activeLeases`；该返回值没有赋给变量或检查，100ms 后即进入 `close()`。`read()`/`write()` 的 `resolveHandle()` 在 `resourceMutex.withLock` 中只读取并返回 handle，之后 block/`resource.transaction()` 在锁外执行；因此 `close()` 获取同一 mutex 只能序列化 handle 指针，不会等正在使用 handle 的业务 block。`RuntimeSessionManagerTest` 的 `seal timeout cancels active write before closing resource` 通过 `awaitCancellation()` 与 `finally` 在 100ms 内合作完成，另一个 observer 测试也使用可取消 Flow；当前没有 `NonCancellable`/不可中断资源操作跨越 grace 的用例。若操作超过 grace，Runtime 可在其仍使用 handle 时调用 close；这是可由实现路径推导出的资源生命周期竞争，现有测试不能证明产品资源确实会发生非合作执行或数据损坏，需先明确/验证实际 Room/driver 取消行为并闭合通用资源 API 合同。

**新增 soft-lock lease 证据：** `SessionLeaseGate.softLock()` 在 `leaseMutex` 内只更新 `lockState` 并发送转换事件；它不等待 `activeLeases`、不取消 `leaseOwners`，也不等待长 observer 收尾。`read()`/`write()` 在进入 block 前取得 lease，完成后直接返回 block 结果，没有再次核对 session 状态；已有 transaction 因此可在 soft-lock 状态发布后继续运行，且 `VaultSessionController.lock()` 随后可发布 `AuthenticationState.Locked` 并返回，而该 lease 尚未结束。新读取会因 `acquireLease().ensureUnlocked()` 被拒绝，但“新工作被拒绝”不等于“既有工作已完成或其迟到结果失效”。当前 Runtime 测试覆盖 soft lock/resume 状态切换，没有 active read/write/observer 跨 soft-lock 的屏障测试；现有 Autofill Task 9 约束最后租约归还时的锁责任，不规定通用 Room 读写的软锁完成合同。需明确这是不是有意允许“锁后已启动操作完成”，并在通用 session owner 与受影响调用端验证，不把并发时序直接定性为已复现数据泄露或错误提交。
