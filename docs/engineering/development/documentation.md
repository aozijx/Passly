# 文档维护约定

## 分类与命名

- 物理目录按产品功能、平台合同、工程工作流和项目记录分类：`product/<feature>`、`platform/{architecture,data,security}`、`engineering/{getting-started,development}`、`project/{decisions,reviews,work/{specs,plans}}`。文件归属按主要 owner 决定，不按阅读路线复制到多个功能目录；确需路径调整时，同步修改入链、规则、生成器和校验任务。
- 文件名使用小写 kebab-case；`docs/README.md` 是唯一完整目录索引，按读者任务和产品功能分组并直接链接主题页。带日期的计划、设计和必要验收依据在索引中按 `YYYY-MM` 分组，物理文件留在 `project/` 的职责目录，不为月份另建重复目录。功能目录可建立真实的 `overview.md` 组合路线、状态 owner 和权威详情页；不能建立只转跳的 `README.md`。生成文件遵循唯一生成器确定的路径，不手工修改内容。
- 一个主题只有一份“当前实现”文档，避免 Design、Implementation、outline 并存。
- 类与包名以仓库当前代码为准；版本号、字段表等易漂移信息尽量链接源码而不是整段复制。
- 多流程功能可以建立子主题目录与真正的 Overview；只有职责 owner、生命周期、合同或读者群确实独立时才拆文件，行数不是拆分理由。Overview 组合链接并简述流程，不复制细节；重复流程只保留一个权威页面，其他主题以链接引用。
- `specs`、`plans` 只保留尚未完成的设计或工作。每个待办只记录下一步和验收条件；完成的勾选项立即移除。
- 实施完成后，把当前合同归入唯一主题页；仍有审查价值的验收证据移到 `reviews/`，否则删除临时计划。迁移前更新入链，生成文档必须通过生成器校验，不能手工修补。
- `project/reviews/` 保存有明确日期和范围的历史审查或交付证据，不作为当前实现合同或活动待办来源；`project/work/{specs,plans}` 只保留未完成设计和开放工作。`docs/README.md` 索引主题页与审查记录，不重复维护计划状态。

## 内容结构

实现主题页统一为：标题；适用时在标题下标明状态；开头简述主题职责；正文按职责、边界、行为流程、失败与清理组织；文末集中列出具体代码位置。只保留与该主题有关的章节，不添加空章节。

标题层级使用一级标题表示文档标题、二级标题表示并列主题、三级标题表示主题内流程。列表用于并列事实，编号列表只用于顺序不可互换的步骤；术语、状态名和路径使用反引号，避免用粗体代替标题。

实现主题页以 `## 代码位置` 作为最后一节，使用表格列出具体类或函数、源码文件和职责。优先标出承载文档所述行为的生产符号；仅列文件名不足以定位时，应补上函数名。正文可保留帮助理解流程的上下文链接，但不重复粘贴整段源码；代码示例只保留解释稳定契约所需的最小片段。Android API、权限和平台回调资料放在代码位置之前。

ADR、审查记录、活动计划、入门说明和生成文件使用各自适合的结构，不强行套用实现主题页模板。复杂流程可使用 Mermaid。迁移旧文档前先核对生产代码、Manifest、Gradle、Proto/Room schema、资源和行为测试；移动文本不等于验证正确。

状态统一使用：

- `状态：当前实现`；
- `状态：已批准，尚未实现`；
- `状态：过渡中`，并明确分隔当前与目标。

语言、平台 API、权限、存储、生命周期、平台回调和框架行为需要核对对应供应方的官方文档。写规则时区分官方保证、Passly 政策与当前实现快照；现有 prose 不能覆盖生产源码，只检查源码字符串的测试也不能单独证明运行时行为。

ADR 统一包含：状态、日期、背景、决策、后果、备选方案和关联资料。已发布 ADR 不删除；决策变化时新增 ADR，并用
`Superseded by` 建立关系。

## 校验

修改文档后至少检查：

- 相对链接目标存在；
- 类名、包名和 Gradle 任务仍存在；
- Mermaid 节点文本不依赖大段实现代码；
- “已实现”和“计划中”有清晰区分；
- 没有密钥、签名凭据或本地路径进入文档。
- 没有重复定义另一个主题拥有的协议；跨主题使用链接。
- dated 计划、完成清单、旧类名和一次性命令没有残留在正式文档。
- 活动计划只含开放事项；完成项已删除，历史验收记录与当前合同分开。
